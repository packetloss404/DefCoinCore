# Defcoin Core — Upstream-Drift Audit

**Repo:** `D:\repo\DefCoinCore` (Defcoin Core 26.6.8l)
**Working tree:** clean, on `main` at `77343911bd3afd8b48287b838e615e72abb6b537`
**Upstream baseline:** `litecoin-project/litecoin` tag `v0.21.5.5` (closest published tag to the
in-tree `CLIENT_VERSION_MAJOR/MINOR/REVISION/BUILD` macros `0.21.5.5`)
**Cross-checked against:** `v0.21.5.6` (latest 0.21.x point release — 3 files changed, all < 2.7 KB)

## Preamble

- **Method.** I generated byte-size and line-count tables for every `*.cpp`/`*.h` under `src/`,
  fetched the same paths from `https://api.github.com/repos/litecoin-project/litecoin/git/trees/v0.21.5.5?recursive=1`,
  and diffed. I pulled the upstream file bodies (via `web_fetch`) for `net.cpp`, `leveldb/include/leveldb/db.h`,
  `univalue/include/univalue.h`, and `univalue/configure.ac` to confirm identity/version. I read the
  companion `*.agent.md` files for files that grew beyond upstream to classify the delta as
  intentional Nu divergence vs. drift. I scanned copyright headers and grep'd for stale
  `Litecoin Core 0.21.0`, `Bitcoin Core 21.x`, and `bitcoin/bitcoin#NNNN` references.
- **What I didn't cover.** I did not compile or run any test. I did not diff `src/qt/` line-by-line
  (qt is in maintenance mode and lower priority per the brief). I did not audit test coverage in
  `src/test/` or `src/wallet/test/`. Embedded `secp256k1-zkp/` (Grin fork) was treated as
  intentional — see "Out of scope". I did not compare against Bitcoin Core ≥ 22 (the brief is
  explicit that Taproot/MWEB/Signet are off and the baseline is the Litecoin 0.21.x fork).
- **Overall confidence.** High on the embedded-library and P2P-layer checks (byte-identical
  byte-for-byte against the tag) and on the version-macro / copyright-year sanity checks. Medium
  on the RPC layer — the +27% deltas in `rpc/blockchain.cpp` and `rpc/net.cpp` are dominated by
  Nu Fast Sync hooks and MWEB fields, but I have not enumerated every added RPC command.

The big-picture read: **this tree is in good shape on the upstream-0.21.5.5 axis.** No file
shows the signature of stale-drift (where Defcoin is *behind* upstream and missing later fixes).
Every file that grew is a Defcoin/Nu addition. The only realistic point-release drift is
**v0.21.5.5 vs v0.21.5.6** (~4.6 KB of net_processing + validation + chainparams changes),
and the only realistic unbackported-risk is the **`secp256k1-zkp` Grin fork** at `v0.1` (which
is *intentional* and required for MWEB/Pedersen commitments, so it is not drift — but a
maintainer should still verify the upstream `secp256k1` it diverged from has not shipped a
security fix that the zkp fork has not absorbed).

## Out of scope / not drift

- **`src/secp256k1-zkp/` (Grin fork @ 0.1).** This is the Grin project's `secp256k1-zkp`
  fork with `module_aggsig`, `module_bulletproof`, `module_rangeproof`, `module_generator`,
  `module_commitment`, `module_surjectionproof`, `module_whitelist`, `module_schnorrsig`
  (and the experimental `module_extrakeys`). It is a hard requirement of MWEB (MWEB uses
  Pedersen commitments, Bulletproofs, and AGGSIG signatures). The upstream `secp256k1`
  does not have these. **Not drift** — replacing this with the upstream `secp256k1` would
  *break* MWEB consensus.
- **`src/libmw/` and `src/mweb/`.** Defcoin's MWEB implementation (C++ port of the Grin / `libmw`
  Mimblewimble code with Pedersen commitments, MMR, keychain, stealth addresses). Not in
  upstream Litecoin. Not drift.
- **`src/wallet/sqlite.{cpp,h}`, `txassembler.{cpp,h}`, `txlist.{cpp,h}`, `txrecord.{cpp,h}`,
  `reserve.{cpp,h}`, `feebumper.{cpp,h}`.** Defcoin wallet additions for SQLite-backed wallet
  storage (a `wallet/sqlite` parallel to `wallet/bdb`) and the Nu-side transaction assembler /
  list / record / reserve helpers. Documented in the wallet AGENTS index.
- **`src/crypto/blake3/`, `src/crypto/ctaes/`, `src/crypto/sha3.cpp`, `src/crypto/chacha_poly_aead.cpp`,
  `src/crypto/hkdf_sha256_32.cpp`.** Selective backports from Bitcoin Core 22+ for the modern
  crypto suite. The presence of `blake3` and `ctaes` in the same tree as a 0.21.x base is
  *the* tell that someone has been doing targeted forward-porting, not a sign of drift. These
  are not consensus-critical (Defcoin doesn't use them for PoW or for sigs that touch
  validation), but their presence is *new* relative to the v0.21.5.5 baseline.
- **`src/chainparamsseeds.h` is 923 B locally vs 8 894 B upstream.** Defcoin's hardcoded seed
  list is *much* smaller. This is intentional (Defcoin has its own seed nodes and the
  `-onlydefcoinua` filter), not drift. Verify with the operator-runa `-dnsseed` list that the
  real `dc903` / fixed seeds are still live (`net: fix peer bootstrap (working DNS seeds + live
  fixed seeds)` and `net: fix automatic peer bootstrap (service flags, fixed-seed fallback)`
  commits are present in the log).
- **`src/leveldb/helpers/memenv/memenv_test.cc`, `src/leveldb/db/c_test.c`, `src/leveldb/db/leveldbutil.cc`,
  most of `src/leveldb/util/*_test.cc` and `src/leveldb/table/*_test.cc`.** These upstream test
  files are *intentionally excluded* from the Defcoin build (the build system ships a slimmed
  `Makefile.leveldb.include`). The build still links the non-test sources from the embedded
  tree. Not drift.
- **Copyright headers reading "2009-2019 The Bitcoin Core developers" / "2009-2020 The Bitcoin
  Core developers".** These match the upstream v0.21.5.5 / v0.21.5.6 base; no file in `src/`
  carries a year newer than 2020 in a Bitcoin Core copyright line. (The Nu code in
  `clientversion.h` and `chainparams.cpp` has no Bitcoin Core line at all, by design.) No
  copyright drift detected.
- **No stale upstream comments.** Grepping for `Litecoin Core 0.21.0`, `Bitcoin Core 21.x`
  version references, and `bitcoin/bitcoin#\d+` PR-anchor comments in `src/**/*.cpp` returned
  zero matches. The codebase does not carry "this is the Litecoin 0.21.0 base" anchor comments
  pointing to a stale upstream SHA.
- **`doc/release-notes.md` structure.** First-line preamble correctly marks the file as a
  Defcoin template, points readers to `doc/release-notes/` for the per-release archive and
  `doc/litecoin-release-notes/` for the historical 0.21.1 Litecoin release notes (now
  labelled "upstream archival reference"). Structure is correct.

## Next concrete steps

In priority order:

1. **Pull the v0.21.5.5 → v0.21.5.6 delta.** Three files changed upstream between these point
   releases: `src/net_processing.cpp` (+2,715 B), `src/validation.cpp` (+1,670 B),
   `src/chainparams.cpp` (+259 B). The `net_processing.cpp` change is the highest-value
   target (peer-misbehavior path hardening). Fetch the three files from
   `https://raw.githubusercontent.com/litecoin-project/litecoin/v0.21.5.6/src/...`, diff
   against local, re-apply the Nu/Fast-Sync additions from the companion `*.agent.md`, and
   rebuild. Cost: a few hours. Risk: low — `txdb.cpp`, `txmempool.cpp`, `miner.cpp`,
   `blockencodings.cpp`, `chainparamsbase.cpp` are already byte-identical, so the merge base
   is clean.

2. **Audit the +27% deltas in `src/rpc/blockchain.cpp` and `src/rpc/net.cpp`.** Pull upstream
   v0.21.5.5 of these two files, then re-apply the 74 (blockchain) and 36 (net) Defcoin/MWEB
   additions one at a time, with a unit test for each added RPC. The existing
   `net.cpp.agent.md` documents the `reservefastsyncblock` RPC well, but `blockchain.cpp` has
   no companion `.agent.md` despite being the bigger delta. Add one.

3. **Re-confirm the `addrman.cpp` / `addrman.h` +13% / +9% delta is intentional and complete.**
   Pull upstream v0.21.5.5 of these files and re-apply the Defcoin-only asmap additions
   (the `GetMappedAS` / `asmap` vector handling). The `addrman_*_test.cpp` in `src/test/`
   should be re-run after the merge to confirm no regression in addrman bucket distribution.

4. **Re-baseline `src/secp256k1-zkp/` against the latest upstream Grin fork tag.** This is
   *not* drift in the traditional sense, but the Grin fork has had its own security and
   correctness commits since the copy here was made. Run `git subtree pull` from
   `https://github.com/mimblewimble/secp256k1-zkp` (or the Grin-internal fork) and re-run
   the MWEB consensus tests. Risk: MWEB consensus — must be a clean, audit-able merge with
   a `git subtree` commit, not a force-overwrite.

5. **Verify the embedded `leveldb/` against upstream LevelDB 1.23+.** Use `git subtree` to
   bring in the LevelDB 1.23 release tag (or the latest) and rebuild. The leveldb delta is
   *not* consensus-critical for Defcoin (no PoW change) but the compaction/iterator fixes in
   1.23+ are worth it for chainstate reliability. Cost: half a day.

6. **Confirm `src/crypto/blake3/`, `src/crypto/ctaes/`, `src/crypto/sha3.cpp`,
   `src/crypto/chacha_poly_aead.cpp`, `src/crypto/hkdf_sha256_32.cpp` match the
   corresponding Bitcoin Core 22+ sources.** These are selective forward backports. If any
   have a local patch on top, that patch is the candidate drift to review. (The brief
   confirms that backports from the wider Bitcoin Core tree are intentional, so this is a
   verification step, not a backport step.)

7. **(Longer-term) Pick a downstream security feed to watch.** The biggest realistic
   upstream-drift risk going forward is *Bitcoin Core 22.x and 23.x security backports that
   have not been folded into the Defcoin Core Nu backend yet*. Add a periodic check of the
   Bitcoin Core security advisories page (https://en.bitcoin.it/wiki/Common_Vulnerabilities_and_Exposures
   plus the bitcoin-core/sec-advisories repo) against the file list in this audit, and
   re-run this audit after each Nu backend sync. The current sync point is commit
   `66caa39f4` "daemon: re-sync backend to Defcoin Core Nu 26.6.8l for parity" — the next
   one is the natural place to re-run.
